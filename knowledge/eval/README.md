# HiBot evaluation set and harness

Silver-label regression set: 45 Sirius EU/CIS tickets (40 `test`, 5 `dev`). Labels are heuristic (footprint in the DB, Jira resolution,
comments), NOT developer-verified; `label_confidence` says how far to trust each one and `needs_human_review` marks the low ones.

| file | content |
|---|---|
| `eval_set.json` | the tickets and labels (generated by `tools/eval/build_eval_set.py`, curated table inside the script) |
| `labeling_notes.md` | one line per ticket: why the label |
| `results_<tag>.md/.json` | scoring output of a run (`tools/eval/score.py`) |

Hold-out: SM-2139009, SM-2139002, SM-2122480, SM-2126600, SM-1777386 were used while developing and form the `dev` split.
Never tune prompts/cards on `test` tickets (cards created from `test` tickets would leak labels).

## eval_set.json ticket
`key, split, stratum, region, problem_type, app, expected_work_order_ids, expected_tenant_id (from ticket_windows.jsonl when known),
expected_classification (code_defect|master_data|access|data_correction|integration|config|user_error|unknown), label_confidence,
label_basis, expected_findings[], needs_human_review, note (<=120 chars own-words paraphrase)`.

`expected_findings` checks (1-3 per ticket, evaluated on report.json + run record):
`wo_resolved{work_order_id,tenant_id}` (preflight resolved it), `manual_fix_detected{from,to}` (report.ticket_window_changes flags a
suspected manual fix with that status change), `no_manual_fix`, `transition_missing{tenant_id,from,to}` (a StatusStep check ran AND the
report text names both ids and a transition/StatusStep wording; heuristic), `query_used{query_id}` (executed in live mode, prepared in
dry-run), `mentions{any[]}` (case-insensitive substring in summary/root cause/evidence/fix steps), `not_code_defect`.

## Run and score
```
python tools/eval/run_eval.py --tag fake1 --llm fake --limit 3                       # dry-run, no DB/LLM
python tools/eval/run_eval.py --tag live1 --llm http --live --split test --delay 3 --resume
python tools/eval/score.py --tag live1 [--split test|dev|all]                        # -> knowledge/eval/results_live1.{md,json}
python tools/eval/build_eval_set.py                                                   # regenerate the set (needs local jsonl files)
```
Run output: `runs/eval_<tag>/results.jsonl` (checkpoint, appended per ticket; git-ignored via `runs/`) and `runs/eval_<tag>/runs/<run_id>/`
(normal HiBot run folders). Options: `--keys A,B`, `--region EU|APAC` (default: per ticket), `--max-steps`, `--max-queries`, `--delay`.

## Metrics (score.py)
* **Reliable labels** = high+medium confidence. Headline accuracy and confidently-wrong use reliable labels only; "all" numbers are also given.
* **Tenant / WO resolution**: expected WO id (and its tenant) appears in the preflight `resolved` list. Only tickets with a known WO / tenant.
* **Classification exact**: report.classification == expected. **Lenient**: also counts config~data_correction and config~master_data
  (symmetric, not transitive); everything else must match.
* **Findings hit rate**: hit checks / all checks.
* **Calibration**: reliable-label exact accuracy per confidence bucket 0-0.4, 0.4-0.7, 0.7-1.0.
* **Honest unknown rate**: `unknown` with confidence < 0.5, over all tickets.
* **Confidently wrong rate** (most important failure metric): classification != expected with confidence >= 0.7, over reliable labels.
* Averages: elapsed seconds, queries (prepared / executed), LLM calls; card match rate; per-stratum breakdown, confusion matrix.
* A run record with an error counts as a miss (never silently dropped).

Caveats: dry-run reports can never resolve WOs, so tenant/WO/footprint metrics are only meaningful with `--live`.
