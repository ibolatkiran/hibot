# HiBot code traceability map

Generated by `python tools/code_map/build.py` (Python 3 stdlib only, deterministic, read-only on the Sirius repos).
Chain modelled: **screen -> API call -> backend endpoint (controller action) -> manager method(s) -> DB objects (SP / function / table / inline SQL)**.

## Regenerate

```
cd d:\repos\HiBot
set PYTHONIOENCODING=utf-8
python tools/code_map/build.py
# optional: --portal --crm --partner --technician --api <path>  --out <dir>
```
Runtime is roughly 15-30 seconds. Re-running with unchanged sources produces byte-identical files.

Security: files matching `appsettings*`, `.env*`, `.env-cmdrc.json`, `translate.js`, `web.config`, `*.pfx`, `*.pem`, `*.key`, `secrets*.json` are excluded at the file-walk level and are never opened. Dirs `node_modules build dist bin obj .git git` are skipped. No connection strings or keys are present in the outputs (only SQL object names, route templates, literal UI/error texts).

## Formats

### frontend_<app>.json
- `axios_instances`: per `src/utils` axios instance, the URL prefix that is prepended (base URL suffix + interceptor prefix such as `/Technician`), and whether it points at a non-Sirius service (`external`).
- `routes`: `{path, component, file, layout, exact, line, closure_files, api_endpoints}` parsed from `src/routes.js` (nested `routes:` arrays and `lazy(() => import())` handled). `api_endpoints` = every endpoint reachable from the route component through the import closure of views/components/layouts.
- `screens`: one entry per file in `src/views` (+ components that call APIs / use i18n): `routes` (route(s) whose component is this file), `reachable_from_routes` (routes whose import closure contains it), `i18n {namespaces, keys[{key,ns,line}], dynamic_t_calls}`, `api_calls [{method, url_template, resolved_endpoint, axios_instance, via, file, line, chain}]`.
  - `via`: `raw` (axios call written in the view/component), `slice` (createAsyncThunk in store/slices), `saga` (view -> action creator -> action type -> saga handler -> api fn), `api` (store/api function without saga).
  - `chain`: the hops, e.g. `view -> actions::taskHistoryRequest -> action-type ...::GET_TASK_HISTORY_REQUEST -> sagas::getArtemisTaskHistory -> api::getArtemisTaskHistory`.
- `api_call_sites`: every axios call site in the app (even if no screen reaches it), with `used_by_screens`.
- `resolved_endpoint` is `Controller/Action` (instance prefix applied, `api/` stripped, query string and params dropped); `path_norm` keeps param positions as `{}`.

### i18n_<app>.json
`translations[lang][namespace][key] = text` for `en` and `tr` (other languages present in `public/locales` are only listed in `languages_available` with namespace counts); `reverse_index[lang][normalized_text] = [[ns,key],...]`; `key_usage["ns::key"] = [screen files]`. To trace a user-quoted message: normalize it (lowercase, trim, replace dynamic parts with `*`), look it up in `reverse_index`, then use `key_usage` to find the screen(s) and `frontend_<app>.json` for routes.

### backend.json
- `endpoints`: `{http_method, route, controller, action, file, line (method signature), attribute_line, line_end, calls[Class.method], db_objects, external_calls, error_messages}` (the last three are what the controller action itself does).
- `methods`: `{class, method, file, line_start, line_end, db_objects[{name, kind: sp|function|table|inline_sql, via: dapper|ef|ado|inline}], calls, external_calls[{kind,target}], error_messages[]}`; overloads are separate rows.
- `interface_implementations`: interface -> implementing classes (used to resolve `_manager.X()` to `TechnicianManager.X`).

### trace_index.json
`frontend_calls` (one row per unique app+method+path: callers, matched backend endpoint, match quality, manager methods reachable to depth 4, db objects, external calls), `by_screen`, `by_endpoint` (reverse: backend endpoint -> screens per app), `endpoint_downstream` (full downstream incl. error messages per endpoint), `unmatched_frontend_calls`, `unused_backend_endpoints`, `stats`.
Match quality: `exact` (verb matches and path segments are compatible: literal segments equal, `{param}` matches anything, optional trailing params allowed), `verb-mismatch` (path compatible but HTTP verb differs), `controller+action` (controller and action name match but the number/shape of path segments differs; probably a query/param mismatch), `verb-mismatch+controller+action`.

## Limitations

- Static, regex + bracket-matching analysis; no real JS/C# AST. JSX text apostrophes and regex literals can occasionally confuse the JS masker; C# raw strings / deeply nested interpolation are approximated.
- Frontend url resolution handles string, template and `+` concatenation, and file-level `const` strings. URLs held in variables built elsewhere, or passed through wrapper functions with a dynamic path, are listed as `unresolved` and excluded from the match-rate denominator.
- Calls to non-Sirius services (`customAxios`, `axiosNotification`, absolute http URLs) are flagged `external` and not matched.
- Saga/action chain resolution relies on `take*(Types.X, handler)` and `type: Types.X` patterns; sagas using string literal types, `takeEvery` with arrays, or dynamic dispatch are missed. Default-exported API objects are narrowed by member name when possible, otherwise the whole object is linked (can over-attribute).
- Screens: a call is attributed to a view if the view (not a nested component) references the thunk/action/api function. `routes` / `reachable_from_routes` / route `api_endpoints` use the import closure, so a route lists everything any nested component could call (superset).
- Matching is by controller + action name (case-insensitive); overloaded routes with the same action but different verbs are disambiguated by verb then path shape. A match means the URL exists, not that the runtime request is accepted (auth filters, tenant routing are not modelled).
- Backend call resolution: `_field.Method()` is resolved through constructor/field types and interface->class maps; calls via dynamic types, `var x = factory.Create()`, static helpers on unknown classes, delegates and DI of generic base types are not followed. Overloads of the same name are merged when following downstream.
- DB objects come from literals (direct or assigned to a local variable), Dapper/ADO/EF call arguments and inline SQL text. SQL built by concatenation across statements, stored in constants/resources, or object names inside dynamic SQL are only partially captured; temp tables, variables and `sys.*` are ignored. SP bodies are not in the repo, so SP -> table dependencies are not covered.
- Error messages are literals assigned to ErrorDescription/ErrorMessage/Message/Description/Error or passed to exception constructors; messages composed at runtime or loaded from resources are not captured.
- External calls are heuristic (HttpClient verbs with literal URLs, `*Client`/Sap/Soap/MailOrbit style types, `new XxxClient()`).
- Only en and tr translation texts are embedded; other languages are listed (name + namespace count).
